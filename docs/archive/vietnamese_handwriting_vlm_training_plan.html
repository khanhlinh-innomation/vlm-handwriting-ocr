2.3 Why line-level data first?

Production match

The intended recognizer receives line crops, so line supervision is the closest training distribution.

Avoid imbalance

110k word samples would dominate a 7.3k-line dataset and shift training toward very short sequences.

Cleaner comparison

One granularity isolates model behavior before adding augmentation strategies.

5.3 Why start with 2 epochs?

The training set is small relative to the model, and Paddle is being fully fine-tuned rather than adapted with LoRA. Full SFT updates the whole model, which increases overfitting and catastrophic-forgetting risk on approximately 5.8k training lines. Therefore, two epochs are used as the initial full run. A third epoch is launched only if validation CER still improves after epoch 2.
  • Validation CER improves from epoch 1 → 2: consider epoch 3.
  • Training loss decreases but validation CER worsens: stop after epoch 2.
  • The selected checkpoint is the epoch with the lowest validation CER.

Training plan, GPU sizing, workload & evaluation

Run order, VRAM planning, escalation rules, workload, and evaluation.

6.1 Prompt consistency

The semantic task is identical for all models: read the image and return the exact transcription with no explanation. Prompt strings or special tokens may differ because each model has a different native multimodal template.

6.2 Kaggle-first compute strategy

StageDefault actionEscalation condition
Environment setupKaggleFramework or CUDA stack cannot run reliably on Kaggle
Smoke trainingKaggleOOM, unsupported multi-GPU requirement, or severe instability
Full trainingKaggle if smoke proves it is feasibleMeasured VRAM exceeds available GPU memory or projected runtime is impractical
Team GPU requestOnly after evidence is collectedRequest includes peak VRAM, required headroom, expected runtime, and reason Kaggle is insufficient
This keeps internal GPU usage evidence-based. The first objective is to make the training pipeline run on Kaggle; team GPU capacity is treated as an escalation path rather than the default.

6.3 GPU VRAM sizing strategy

GPU VRAM is distinct from system RAM. System RAM holds dataset/preprocessing/runtime objects, while GPU VRAM is used for model weights, activations, gradients, optimizer states, and temporary tensors. The initial ranges below are planning estimates, not hard requirements.

ModelMethodInitial planning estimateInitial platform plan
GLM-OCR ~0.9BLoRA8–12 GB VRAMKaggle first
NaviDC ~1.2BLoRA12–20 GB VRAMKaggle first; team 24GB+ if needed
PaddleOCR-VL ~1BFull SFT24 GB+; 40 GB+ preferredKaggle smoke first; team GPU likely for full SFT if OOM

Peak VRAM depends on micro-batch size, image resolution, visual-token count, sequence length, BF16/FP32, gradient checkpointing, Flash Attention, frozen modules, optimizer choice, and framework implementation.

VRAM estimate→ Kaggle smoke run→ measure peak VRAM→ measure throughput→ Kaggle full run or team GPU request

6.6 Smoke-run measurements

Each smoke run should record at least:

  • Peak GPU VRAM
  • Samples/sec and steps/sec
  • Wall-clock time
  • Training/validation loss
  • Whether save → reload → inference works
  • Any OOM, compatibility, or data-processing issue

6.7 Evaluation

MetricPriorityMeaning
Strict CERPRIMARYCharacter-level OCR error; Unicode NFC only
WERSecondaryWord-level error
Exact-Line AccuracySecondaryPercentage of exact full-line matches
Diacritic ErrorDiagnosticVietnamese diacritic failure analysis
Peak VRAM / training timeOperationalCompute planning and reproducibility

6.8 Decision rules

  • Do not use the test set for epoch selection or hyperparameter tuning.
  • Best checkpoint = lowest validation CER.
  • If validation CER worsens while training loss keeps decreasing, treat this as an overfitting signal.
  • If save → reload → inference fails, do not launch the full run.
  • Request a team GPU only after Kaggle smoke evidence demonstrates a concrete need.
